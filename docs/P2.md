# Part 1: Establish the input and run ingestion

### Input source and BigQuery Location
- **Google Cloud Project:** `universal-code-508122-p8`
- **BigQuery Dataset:** `books_project`
- **Dataset Location:** `US`
- **Source and Raw Table:** `universal-code-508122.books_project.books` (This is the raw dataset I uploaded to BigQuery and is only a small subset of the source table on the Library's website)
- **Curated Table:** `universal-code-508122-p8.books_project.books_curated`
- **Supporting Table:** `universal-code-508122-p8.books_project.books_final` (This came about after further edits to the curated table)

The `book` table is the Raw table and contains 2,000,000 records representing a sample of library checkout data from Jan 2006 - Dec 2025. The raw table preserves the imported source fields and values. The curated table is a consolidated analytical dataset of grouping records with matching values across the dataset and checkout fields, as well as summing checkout counts. The supporting table contains additional publication year parsing. 

### Source grain
Each record represents the checkout activity for a title (along with other information on the book) during a particular month and year. It includes the checkout count, creator, ISBN, publisher, publication year, material type, checkout type, usage class, and subject information. 

### Ingestion and raw preservation
The existing `books` table that was uploaded to BigQuery was kept as the raw layer. It contains 2 million rows and 12 columns. All of this was retained as is, along with the imported data types. The raw table serves as the starting point for the curated table. The source dataset has over 51 million records, therefore, the raw and curated tables are samples of the data and is not a full visual of the source data. 

### Reproducibility and source limitations
Because this is a sample dataset and not a complete record of all Seattle Public Library checkout activity, analysis results should be understood as sampled checkout activity rather than total library checkouts as a way to inform publishing companies of past and current trends. 

# Part 2: Build curated at the intended grain

### Curated table and intended grain
The curated table is `universal-code-508122-p8.books_project.books_curated`. Each curated row represents the combined checkout count for a particular combination of checkout year, checkout month, title, creator (author), ISBN, publisher, publication year, subjects, material type, checkout type, and usage class. The `checkouts` field is the measure being aggregated, not a part of the grouping key. ISBN will likely be removed from further analysis as most records are missing this value.

### Transformation and consolidation rules
The curated table was created using the `CREATE OR REPLACE TABLE AS SELECT` statement. The transformation groups the records by the 11 fields stated above and calculates `SUM(checkouts)` for each group. This preserves combined checkout counts while consolidating identical records.

In P1, the grain did not include ISBN, publisher, publication year, or subjects. Further testing of this grained showed 955 repeated groups, 1,796 excess rows, and 691 groups with different checkout values. This may be due to different catalog attributes. The extended grain retains all the information but also produced zero repeated groups in the curated table.

### Missing values and data validation
The curated table preserved source fields and data types and does not replace missing values. Records with matching missing values in grouping fields were grouped together by BigQuery.

The SQL includes validation queries for missing titles, creators, ISBNs, subjects, publishers, publication years, checkout dates, and checkout counts. Negative, invalid, and unusual values were also investigated. Check the `P2_sql` file in the code folder within the repository. 

Publication year parsing was handled separately in the supporting `books_final` table. The original `publicationyear` value is preserved in `books_curated`. The supporting table adds extracted publication year and copyright year fields for additional analysis if wanted. When both years were present, they were treated as separate values: the publication year represents when the work was published whereas the copyright year represents its copyright date. This distinction helps to prevent copyright dates from being misinterpreted as publication dates. 

### Raw to curated reconciliation
  |Measure                 |    Raw (`books`)|   Curated (`books_curated`)|
  |-------------------------| ---------------| ---------------------------|
  |Row count                 |      2,000,000 |                  1,999,999|
  |Total sampled checkouts   |      6,967,138   |                6,967,138|

The reason the curated table contains one less row is because identical records were consolidated. The total sampled checkouts remained the same as aggregation preserved checkout counts despite record consolidation.

The `checkouts` field is carried from raw to curated through `SUM(checkouts)`. The resulting measure supports the audience facing analysis of sample checkout activity grouped together.

After creating `books_curated`, I ran validation queries to check the checkout measures and date fields. These are the results:
- 0 `NULL` checkout counts
- 0 zero checkout counts
- 0 negative checkout counts
- 0 missing checkout years
- 0 missing checkout months
- 0 invalid checkout months (i.e. outside the range of 1-12)

Additionally, no missing titles, material types, checkout types, or usage classes were found. These are the attributes that did contain missing values:

  |Field             |   Missing records |  Missing percentage|
 | ------------------ |----------------- |--------------------|
 | Creator              |        323,203   |            16.16%|

Missing values were retained rather than being replaced. ISBN will not be able to be used as a standalone identifier for future analysis. 

# Part 3: Run and interpret two acceptance checks

### Acceptance test 1: confirm the grain
The first acceptance check evaluated whether the curated table contained one record per composite grain. Testing of the initial P1 grain showed that the original proposed grain was not sufficiently detailed. Therefore, the grain was expanded to include ISBN, publisher, publication year, and subjects.

**Result: Passed.** The curated table satisfies the tested composite-grain uniqueness rule.

### Acceptance test 2: confirm monthly coverage and interpret sample for audience

The second acceptance check evaluated whether the dataset provides sufficient and relatively consistent monthly coverage to support historical checkout trend analysis. The expected period contains 240 calendar months. Analysis showed no missing months, however the sampled records per month varied considerably. 

- Expected months: 240
- Months with records: 240
- Missing months: 0
- Minimum monthly record count: 2
- Maximum monthly record count: 15,000
- Average monthly record count: approx. 8,333

Further checks identified May 2020 as an unusually low-coverage month, containing only 2 records and 6 sampled checkouts. This occurred early during the COVID-19 pandemic, when library access was disrupted, however, that is not enough to establish why this sample was so small. 

**Result: Passed with a limitation.** The dataset covers every month in the required 2006-2025 period, but the substantial variation in monthly sample sizes means that the monthly sampled checkout totals should not be automatically interpreted as changes in demand. For the acquisition committee, historical findings should therefore be described as patterns in the available sampled checkout data.

### Additional limitation

Catalog completeness remains a limitation. For example, 83% of curated records have no ISBN and 21% have no publication year. These missing values can affect analysis, although there were kept as is. 

# Part 4: Reproducibility and run order
The SQL queries are stored in a file in the repository's `code ` folder. This file contains source inspection, grain investigation, curated table creation, data quality checks, raw to curated reconciliation, publication year cleaning, and monthly coverage analysis.  The queries are organized by purpose with comments used as headings. The SQL is also stored in its original, unorganized, form in BigQuery as `P2_sql`.

### Run order
The repeatable process is:
1. Confirm that the raw table `universal-code-508122-p8.books_project.books` is available.
2. Execute the `CREATE OR REPLACE TABLE ` statement to create `books_curated` from raw.
3. Run the curated validation queries to check checkout counts, checkout dates, missing attributes, and repeated composite grain groups.
4. Run the raw-to-curated reconciliation query to compare row counts and total sampled checkouts.
5. Execute the supporting publication year cleaning statement to create `books_final` when publication year analysis is required.
6. Run monthly coverage checks to identify missing months and unusually low sample counts.

It is important to note that this process can reproduce the curated and supporting tables from the raw table as it currently exists in the BigQuery project, but cannot reproduce the original 2 million record sample from the larger Seattle Public Library dataset.
